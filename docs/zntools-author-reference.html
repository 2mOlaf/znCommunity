ZNTools Authoring Guide

PowerShell 7+ Module Author Reference

This guide documents internal helpers and the required standards for adding new ZNTools commands. Use this when authoring or modifying module functions.

Module structure

  • ZNTools/ZNTools.psm1 dot-sources all Private/*.ps1 (sorted by name), then all Public/*.ps1, then calls Ensure-ZNWelcomeShown.
  • ZNTools/ZNTools.psd1 exports public functions and applies DefaultCommandPrefix = 'ZN'.
  • Place public command functions in ZNTools/Public. Related small functions may share a file.
  • Place private helpers in ZNTools/Private. Prefix filenames with a number to control load order.
Prefixing Public functions are defined without the ZN prefix (e.g., Get-Asset) and exported with a default prefix via the manifest. The effective command is Get-ZNAsset. Add every new function name (without prefix) to FunctionsToExport in ZNTools.psd1.

Standard block

Every public function must include comment-based help with .SYNOPSIS and an Author: line inside .NOTES, and call the banner/welcome block. The banner call pattern depends on command type — see Banner guidance below.

Do not use a .AUTHOR tag .AUTHOR is not a recognized PowerShell comment-help keyword. Its presence anywhere in the comment block silently breaks Get-Help parsing for the entire block — .SYNOPSIS, .DESCRIPTION, .PARAMETER, and .EXAMPLE all render blank, not just the author line. Put Author: <name> inside .NOTES instead — this is what Get-ZNAuthorFromCommand parses to populate the console banner. If a function already has other .NOTES content, append the Author: line inside that same block rather than adding a second .NOTES tag — a second occurrence silently wins over the first instead of merging with it.
# Help metadata (required in every public function) .SYNOPSIS <short summary> .NOTES Author: <author name> # Full banner block — use for entry-point commands (see Banner guidance) Ensure-ZNWelcomeShown $author = Get-ZNAuthorFromCommand -CommandName $MyInvocation.MyCommand.Name Show-Banner -Author $author -ScriptName $MyInvocation.MyCommand.Name

Add a new command

  1. Create a .ps1 file in ZNTools/Public.
  2. Define the function without the ZN prefix (e.g., Get-MyThing).
  3. Add comment-based help including .SYNOPSIS, .PARAMETER, and an Author: line in .NOTES.
  4. Include the appropriate banner block (see Banner guidance).
  5. For API commands, use the API helper functions. For data-driven commands, call Assert-ZNAssetDataLoaded.
  6. Add the function name (without prefix) to FunctionsToExport in ZNTools.psd1.
  7. Update ZNTools/README.md and zntools-user-reference.html.

Command Patterns

Internal

API-backed commands

Use Get-ZNApiKey, Get-ZNApiBaseUrl, and Get-ZNApiHeaders to normalize authentication. Use Get-ZNErrorBody in error handling. These commands show the full banner.

$token = Get-ZNApiKey -ApiKey $ApiKey $baseUrl = Get-ZNApiBaseUrl -ApiKey $token -ApiUrl $ApiUrl $headers = Get-ZNApiHeaders -ApiKey $token try { $response = Invoke-RestMethod -Uri "$baseUrl/example" -Headers $headers -Method Get } catch { $errBody = Get-ZNErrorBody $_ Write-Error "Request failed: $($_.Exception.Message)" if ($errBody) { Write-Error "Response body: $errBody" } }

Data-driven commands (Asset Browser)

Commands that operate on session-loaded JSON data (e.g., the asset browser query functions) follow a different pattern. They do not make API calls and do not display the full banner. Call Assert-ZNAssetDataLoaded at the top to ensure data is available.

# Data-driven command — no banner, no API helpers function Get-MyAssetQuery { [CmdletBinding()] param() Assert-ZNAssetDataLoaded # use $script:ZNAssets, $script:ZNClusterMap, etc. $script:ZNAssets | Where-Object ... | ConvertTo-EnrichedAsset }
When to use which pattern Use the full banner + API helpers for commands that are clearly entry points (health dashboard, service management, data loader). Skip the banner for lightweight query functions that users may pipe in a single expression — showing a full ASCII banner on every Where-Object would be disruptive.

Banner guidance

Command typeBanner callRationale
Entry-point / API commands Ensure-ZNWelcomeShown + Show-Banner User-facing entry points that stand alone.
Data query functions None Called repeatedly in pipelines; banner output would be disruptive.
Scheduled / metric commands None (by design) E.g. Get-DisconnectedAssetMetric. Meant to run unattended on a schedule and feed a metrics/dashboard pipeline — ASCII art and timestamped log lines in that output are pure noise, and risk getting mixed into captured stdout. On error, these commands should Write-Error and return nothing rather than a fabricated zero-value result, so a real failure can't silently read as "zero" on a dashboard.

Health maps

Private/20-HealthMaps.ps1 defines script-scoped maps used by Show-HealthDashboard:

  • $script:HealthStatus
  • $script:SeverityOrder
  • $script:SeverityColor
  • $script:IssueCodeNames
  • $script:AssetMonitorType
Keep these traceable to the OpenAPI spec, not guessed $script:IssueCodeNames and $script:AssetMonitorType are transcribed verbatim from the healthIssue.issueCode and assetStatus enum descriptions in the ZN OpenAPI spec (including the spec's own typos, e.g. "Unexpted GPO Rules") — an earlier version of $script:IssueCodeNames had plausible-looking but entirely fabricated names for every single code (e.g. code 26 shown as "Hardware Incompatibility" when the real API meaning is "SSH Password Incorrect"). If you add a new code, copy its description straight from the spec rather than inferring one from the code number or name.

Security event shared helpers

Defined in Private/50-SecurityEventShared.ps1. Shared by Get-SecurityEventRate and Get-SecurityLogAnalysis so both commands agree on Event ID descriptions, which IDs Zero Networks requires, and how "events per second" is computed.

SymbolTypeDescription
$script:ZNRequiredEventIds State Flat array of Event IDs that Zero Networks segmentation depends on. Update this single array as requirements change — callers flag membership with $id -in $script:ZNRequiredEventIds.
$script:ZNSecurityEventDescriptions Lookup Event ID → friendly description. Covers common Security-log events plus every ID referenced by $script:ZNRequiredEventIds, including ones from the System log and the Windows Firewall With Advanced Security log (relevant when -LogPath points at a non-Security .evtx).
Get-ZNBucketedRate Function Computes average/peak events-per-second from a bucket-index → count dictionary. Takes -Buckets, -Count, -TotalSeconds, -BucketSeconds. Both rate-reporting commands call this so "events/sec" means the same thing everywhere in the module.
Why Get-SecurityLogAnalysis doesn't call Get-SecurityEventRate directly Both commands now support offline -LogPath archives, but Get-SecurityLogAnalysis still needs rates for every Event ID it encounters in a single pass, not just a caller-specified -EventId list — calling Get-SecurityEventRate once per discovered ID would mean re-reading the log (or file) that many times. Instead it accumulates its own per-ID rate buckets during the single read pass it already does, then calls the shared Get-ZNBucketedRate helper directly. That keeps the rate math identical between the two commands without re-querying the log.
Get-SecurityEventRate offline window: full pass vs. targeted peek With -LogPath and no -Period, the analysis window is the actual observed span of matching events, so every event matching -EventId must be read to find the min/max timestamp — the same pass that already produces Count, so it's not extra work. With -LogPath -Period, the command first does a cheap single-event peek (-MaxEvents 1, relying on Get-WinEvent's newest-first default order for offline files) to anchor the window to the most recent matching event, then filters the real query by StartTime/EndTime — the same FilterHashtable mechanism the live-log path already uses — rather than scanning the whole file.

Disconnected asset helpers

Defined in Private/60-DisconnectedAssets.ps1. Shared by Show-HealthDashboard and Get-DisconnectedAssetMetric so both commands page assets and detect disconnection identically — but the two commands deliberately fetch from different endpoints. See the callout below before adding a new caller.

FunctionDescriptionNotes
Get-ZNPagedAssets Cursor-pages through any assets-shaped list endpoint (searchAssetsResponse), with an optional -Filters array. Shared plumbing behind Get-ZNAllAssets and Get-ZNMonitoredAssets — implement new asset-fetch variants on top of this rather than duplicating the pagination loop. Uses _cursor/nextCursor, not _offset: offset paging drifts when the asset list changes mid-fetch, which produced ~9% duplicate entries on a 7.7k-asset tenant before this was fixed. -Filters takes an array of @{ id; includeValues; excludeValues } hashtables — this is the same _filters JSON contract the portal UI sends, confirmed against the live API but not documented with a concrete schema in the OpenAPI spec. Enum-typed filter values (e.g. healthStatus) must be passed as strings ("2", not 2) or the API rejects them.
Get-ZNAllAssets Fetches every asset (monitored or not) from GET /assets, optionally scoped to one cluster via -DeploymentsClusterId. Use this where the full population is genuinely required — e.g. Show-HealthDashboard always uses this, and its -IncludeNA path specifically needs the Not-Monitored assets that Get-ZNMonitoredAssets excludes. No internal logging — callers wrap it with their own Write-Log/Write-Host as appropriate for their context.
Get-ZNMonitoredAssets Fetches every asset from GET /assets/monitored (no filter parameters). Used only by Get-DisconnectedAssetMetric. Excludes assetStatus 1 (Not Monitored) and similar unmonitorable statuses — roughly halves the fetch, and every cluster/monitor-type bucket the metric reports is still represented among monitored assets, so nothing drops out of the per-cluster breakdown. Deliberately has no health-status/disconnected/cluster filter parameters — see the callout below for why.
Get-ZNAssetClusterLabel Resolves the deployment-cluster display label for a single asset. Returns deploymentsCluster.name when present. Otherwise the asset has no Segment Server deployment cluster — per the assetStatus enum, that includes 7 (Cloud Connector) and 14 (Lightweight Agent), which are monitored directly rather than routed through a customer-run Segment Server — so the label becomes Unclustered (<monitor type>) via the $script:AssetMonitorType map in Private/20-HealthMaps.ps1, instead of one flat Unclustered bucket. Used by both Get-ZNDisconnectedAsset and Get-DisconnectedAssetMetric so they bucket identically.
Get-ZNDisconnectedAsset Filters an asset list down to currently-disconnected assets, optionally requiring a minimum number of days disconnected. Deployment cluster (ClusterId/ClusterName) comes from Get-ZNAssetClusterLabel — no separate cluster lookup call needed. Also returns the asset's raw AssetStatus and its mapped MonitorType label.
/assets/monitored looks like a safe shortcut. It isn't, for everything.

/assets/monitored and its server-side _filters (healthStatus, assetDisconnectedSince, deploymentsClusterId, ...) are real and documented via GET /assets/monitored/filters — and they're tempting, because they avoid pulling the full tenant just to filter it client-side. An earlier version of Show-HealthDashboard used the healthStatus filter for exactly that reason, verified against a 7.7k-asset tenant to return the identical non-healthy set as the full fetch.

A second tenant broke that assumption: an asset with assetStatus 1 (Not Monitored) had a real, non-N/A healthState.healthStatus — stale from before it stopped being monitored. /assets/monitored excludes assetStatus 1 unconditionally, by definition of the endpoint, regardless of what filter you pass — so the dashboard silently reported "All assets are healthy" while hiding a real error. The same gap applies to assetDisconnectedSince: ~0.7% of disconnected assets on a test tenant had unmonitorable statuses that endpoint excludes.

Rule of thumb: Get-ZNMonitoredAssets//assets/monitored is fine for a metric where "an asset ZN isn't monitoring isn't actionable anyway" is an acceptable framing (that's why Get-DisconnectedAssetMetric uses it). It is not fine for anything whose job is to surface real problems to a human — use Get-ZNAllAssets (full /assets) there, even though it's slower. Don't reintroduce filter parameters on Get-ZNMonitoredAssets without redoing this verification against more than one tenant.
