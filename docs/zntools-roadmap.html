ZNTools Module Roadmap

Module Development Community → ZNTools Roadmap

Community scripts that have proven operational value are being formalized into the ZNTools PowerShell module — generalized, hardened, and given the standard module contract. This page tracks what's coming, where it comes from, and what it will look like when it ships.

Living document This roadmap is updated as commands move through design and implementation. The source markdown lives at docs/zntools-roadmap.md. Community scripts referenced here remain available as standalone scripts in the Community repository until the module command ships.

Guiding Principles

A community script graduates to a module command when it meets most of these criteria:

Broad applicability
Useful to any Zero Networks operator, not just one customer topology or third-party product.
Generalizable parameters
The current script solves 80% of the need. The module command solves 100% with proper parameter sets.
Pattern consolidation
Two or more scripts solve the same problem at different levels of polish. The module command replaces them both.
API surface ownership
The operation wraps a ZN REST API endpoint that ZNTools should "own," removing the need for every operator to re-invent the HTTP calls.
Production hardening
The script logic is solid but needs -WhatIf, structured error output, batch retry, and consistent result objects to be production-safe.
Module contract
Private helpers (Get-ZNApiHeaders, Get-ZNApiBaseUrl, Parse-JWT) replace inline HTTP setup. The ZNTools banner is shown.

Tier 1 — Direct Formalization

Scripts that map cleanly to one new command

Source code is already solid. The work is adopting the module contract: swap inline HTTP headers for private helpers, add SupportsShouldProcess, and surface structured output objects.

Test-ZNConnectivity Planned
Diagnostics

Source

  • ZNConnectivityTest.ps1

Evolution

The script is console-only today — pass/fail printed per endpoint. The module command returns structured objects so results can be piped, exported, or acted on programmatically. The endpoint list itself is maintained by the module and versioned with module releases.

What changes

  • Returns [PSCustomObject[]] (endpoint, port, tcpSuccess, dnsSuccess, latencyMs)
  • Adds -Endpoint to target a subset; -Quiet to suppress console output
  • No API key required — connectivity test runs without authentication

Signature

Test-ZNConnectivity [-Endpoint <string[]>] [-PassThru] [-Quiet]
Add-ZNTrustedAddress / Remove-ZNTrustedAddress Planned
Settings

Source

  • Add-ZNTrustedInternetAddresses.ps1

Evolution

The script is additive-only and file-input-only. The module commands support pipeline input, individual IPs as arguments, and a paired Remove command — making them composable with the rest of the pipeline.

What changes

  • -IPAddress accepts [string[]] (pipeline-bindable) as well as file path
  • Paired Remove-ZNTrustedAddress for removal
  • Uses module private API helpers; returns the updated address list

Signature

Add-ZNTrustedAddress [-IPAddress] <string[]> [-ApiKey <string>] [-WhatIf] Remove-ZNTrustedAddress [-IPAddress] <string[]> [-ApiKey <string>] [-WhatIf]
Export-ZNAuditLog Planned
Audit

Source

  • Get-AuditLogByTimeRange.ps1

Evolution

Interactive prompts and manual ISO date string entry are replaced with typed [DateTime] parameters. A -Last shorthand removes the need to calculate timestamps. When no output path is given, objects flow to the pipeline for further filtering or formatting.

What changes

  • -Start / -End accept [DateTime]; -Last accepts [TimeSpan]
  • -AuditType filter using the enum the script already defines internally
  • Pipeline-first: objects returned when no -OutputPath is given; CSV written when path provided

Signature

Export-ZNAuditLog -Start <DateTime> -End <DateTime> [-AuditType <AuditType[]>] [-OutputPath <string>] [-ApiKey <string>] Export-ZNAuditLog -Last <TimeSpan> [-AuditType <AuditType[]>] [-OutputPath <string>] [-ApiKey <string>]
Approve-ZNRuleCleanup Planned
Destructive

Source

  • Approve-ZNProposedDeletes.ps1

Evolution

The script already has -WhatIf and the two scope filters. The module command extends scope to outbound rules and returns a per-rule result object for audit logging.

What changes

  • -Direction Inbound|Outbound|Both (script is inbound-only today)
  • Returns [ZNRuleCleanupResult] per rule (ruleId, approved, reason, whatIfOnly)
  • Standard SupportsShouldProcess pattern for -WhatIf

Signature

Approve-ZNRuleCleanup [-Direction <string>] [-InactiveAssetsOnly] [-NoHitsOnly] [-ReasonFilter <string>] [-ApiKey <string>] [-WhatIf]
Find-ZNConflictingGPO Planned
Active Directory

Source

  • Get-ADGPOsWithFWRules.ps1

Evolution

Replaces console-only output with structured objects and adds parallel GPO inspection for large environments.

What changes

  • Returns [ZNConflictingGPO] objects (GPO name, GUID, conflicting paths)
  • Parallel GPO inspection with ForEach-Object -Parallel
  • -ExcludeGPO <string[]> to suppress known-safe exceptions

Signature

Find-ZNConflictingGPO [-Domain <string>] [-ExcludeGPO <string[]>]

Tier 2 — Pattern Consolidation

Multiple scripts → one generalized command

Each entry here replaces 2–4 community scripts that solve the same problem at different levels of polish. The module command is the "one function to rule them all" — hardened, fully parameterized, and pipeline-composable.

Get-ZNStaleAsset In Design
4 scripts consolidated

Sources

  • get-AssetsStaleConnection.ps1 — disconnected + old lastLogon
  • Get-NoIPAssets.ps1 — no IP addresses registered
  • auditMonitoredAssets.ps1 — expected vs. actual monitored
  • get-assetAuditDates.ps1 — last audit event per asset

Evolution

Four scripts probe different "staleness" dimensions. Three store results in a variable with no further processing; one requires two side-input files. The module command unifies all stale-detection strategies under one interface with composable -Condition filters and a consistent output object.

What changes

  • -Condition NoIP|Disconnected|NotMonitored|All (combinable)
  • -DisconnectedDays replaces hardcoded 180-day variable
  • -CompareFrom accepts pipeline or array, replacing the CSV file requirement
  • Returns consistent [ZNStaleAsset] objects (AssetId, Name, Condition, LastSeen, Recommendation)

Signature

Get-ZNStaleAsset [-Condition <StaleCondition[]>] [-DisconnectedDays <int>] [-CompareFrom <string[]>] [-ApiKey <string>]
Invoke-ZNLearning In Design
4 scripts consolidated

Sources

  • Add-AssetsToLearning.ps1 — file-based input, resolves FQDNs
  • Move-ProtectToLearning.ps1 — all protected → unprotect → queue
  • set-extendLearning.ps1 — extend queued assets by N days
  • Unprotect-ZNLearningButNotConnected.ps1 — unprotect disconnected learning assets

Evolution

These four scripts represent the full asset learning lifecycle — each requires manual editing to configure its inputs. The PSGallery module has Invoke-ZNAssetNetworkQueue but without maintenance window support, file-based input, or the extend/cleanup patterns. The module command makes all of it composable and non-interactive.

What changes

  • -AssetId (pipeline-bindable), -FromFile, and -FromProtected parameter sets
  • -MaintenanceWindowId — maintenance window support the PSGallery module omits
  • -ExtendOnly — only extends in-learning assets, does not requeue
  • -CleanupDisconnected — finds and unprotects disconnected learning assets
  • Batching (100/call) and progress bar managed internally

Signature

Invoke-ZNLearning [-AssetId <string[]>] [-FromFile <string>] [-Days <int>] [-MaintenanceWindowId <string>] [-ApiKey <string>] [-WhatIf] Invoke-ZNLearning -FromProtected [-Days <int>] [-ApiKey <string>] [-WhatIf] Invoke-ZNLearning -ExtendOnly [-Days <int>] [-ApiKey <string>] [-WhatIf] Invoke-ZNLearning -CleanupDisconnected [-ApiKey <string>] [-WhatIf]
New-ZNOTAsset In Progress
2 scripts consolidatedOT / IoT

Sources

  • CreateOTAssets.ps1 — generation 1: CSV import, type hardcoded to 12 (Hypervisor)
  • New-OtAsset.ps1 — generation 2: full type support, JWT URL detection, dry-run, single or CSV

Evolution

New-OtAsset.ps1 is already PS7+, reads the API URL from the JWT, supports all 28 OT device types, and has dry-run mode. It is functionally the generation 2 of this command. The module command is generation 3: swap ad-hoc JWT decoding for Get-ZNApiBaseUrl, adopt the ZNTools banner, promote -DryRun to standard -WhatIf.

What changes

  • Uses Get-ZNApiBaseUrl / Get-ZNApiHeaders from module private helpers
  • -Type becomes a [ValidateSet] covering all 28 OT device types by name
  • -DryRun → standard -WhatIf pattern
  • Returns [ZNAssetResult] object (assetId, displayName, ip) for pipeline use

Signature

New-ZNOTAsset -IPAddress <string> -Name <string> [-Type <OTAssetType>] [-Fqdn <string>] [-ApiKey <string>] [-WhatIf] New-ZNOTAsset -CsvFilePath <string> [-ApiKey <string>] [-WhatIf]
Set-ZNGroupMembership / New-ZNEnvironmentGroup Planned
3 scripts consolidated

Sources

  • Update-ZNGroupMembers.ps1 — CIDR → ZN item ID encoding → PUT members
  • Add-AssetsToTagGroup.ps1 — CSV assets → batch add to tag group
  • create-GroupEnv.ps1 — CSV with environment column → create groups + members

Evolution

The CIDR → ZN item ID encoding in Update-ZNGroupMembers.ps1 is a non-obvious bit of platform knowledge (b:12{hexIP}{hexMask}) that belongs in the module, not every operator's clipboard. These three scripts reveal a core gap: the PSGallery module handles tag groups but has nothing for custom groups, CIDR input, or table-driven group creation.

What changes

  • CIDR → b:12{hex} encoding lives in a private module helper, reusable by any command
  • -GroupId accepts any group type (custom g:c:*, tag g:t:*)
  • -MembersFromCidr, -MembersFromCsv, and -MembersFromAssetId parameter sets
  • -Replace flag for full membership replacement vs. additive (default)
  • New-ZNEnvironmentGroup handles the auto-create-and-verify pattern from create-GroupEnv.ps1

Signature

Set-ZNGroupMembership -GroupId <string> [-MembersFromCidr <string[]>] [-MembersFromCsv <string>] [-Replace] [-WhatIf] [-ApiKey <string>] New-ZNEnvironmentGroup -CsvFilePath <string> [-CreateIfMissing] [-WhatIf] [-ApiKey <string>]
Set-ZNAssetCluster / Get-ZNDeploymentCluster In Progress
Deployment Clusters

Source

  • Pin-AssetsToClusters.ps1 — the most mature community script (PS7+, dry-run, OU, CSV, cluster listing)

Evolution

This script is functionally module-ready. The primary work is adopting the module contract: swap inline headers for Get-ZNApiHeaders, adopt the ZNTools banner, promote -DryRun to -WhatIf, split cluster-listing into its own Get-ZNDeploymentCluster command, and surface output objects through the pipeline.

What changes

  • Inline JWT decode and header construction → module private helpers
  • -DryRun → standard [CmdletBinding(SupportsShouldProcess)] -WhatIf
  • -ListDeploymentClusters split into Get-ZNDeploymentCluster (single-responsibility)
  • Output objects surface through the pipeline

Signature

Set-ZNAssetCluster -AssetId <string> -DeploymentClusterId <string> [-Unpin] [-WhatIf] [-ApiKey <string>] Set-ZNAssetCluster -OUPath <string> -DeploymentClusterId <string> [-Unpin] [-WhatIf] [-ApiKey <string>] Set-ZNAssetCluster -CsvPath <string> [-Unpin] [-WhatIf] [-ApiKey <string>] Get-ZNDeploymentCluster [-ApiKey <string>]

Tier 3 — Expanded Capabilities

Significant redesign — scope expanded beyond the source scripts

These scripts have good ideas and useful patterns, but the module command needs to be substantially broader than what the source script does today.

Invoke-ZNIdentityLearning Planned
Identity

Sources

  • Add-ClientsToIdentityLearning.ps1 — clients only
  • get-currentSVCAccounts.ps1 — service accounts only

Evolution

Two separate scripts, each hard-scoped to a single asset or user type. Together they represent the full identity learning onboarding workflow. The module command generalizes both under one interface with asset-type and user-type targeting.

What changes

  • -AssetType Clients|Servers|OT for asset-side queuing
  • -UserType ServiceAccount|User for user-side queuing
  • -ActiveWithin <int> replaces hardcoded 180-day filter

Signature

Invoke-ZNIdentityLearning -AssetType <string> [-Days <int>] [-ApiKey <string>] [-WhatIf] Invoke-ZNIdentityLearning -UserType <string> [-ActiveWithin <int>] [-Days <int>] [-ApiKey <string>] [-WhatIf]
Update-ZNBlockRule Planned
Block Rules2 scripts consolidated

Sources

  • Update-ZNBlockRulewithRiskyIps.ps1 — add risky IPs from last 24h activity
  • Update-ZNOutboundBlockfromURLFile.ps1 — replace outbound block with URL file

Evolution

Two scripts, two sources, two different behaviors (additive vs. replace). The module command expresses this cleanly through parameter sets.

What changes

  • -Direction Inbound|Outbound is explicit; inbound-only limitation removed
  • -AddFromActivity with -ActivityHours and -RiskLevel
  • -FromUrlFile <path> with -Replace flag

Signature

Update-ZNBlockRule -RuleId <string> -AddFromActivity [-ActivityHours <int>] [-RiskLevel <string>] [-WhatIf] [-ApiKey <string>] Update-ZNBlockRule -RuleId <string> -FromUrlFile <string> [-Replace] [-WhatIf] [-ApiKey <string>]
Import-ZNAssetLabel Planned
Labels

Source

  • Import-AssetLabels.ps1

Evolution

The script requires ImportExcel — a heavyweight dependency just to read an .xlsx file. The core operation (resolve asset, POST labels) is broadly useful. The module command switches to CSV input and adds a single-label interactive mode.

What changes

  • Accepts CSV (not Excel); no ImportExcel dependency
  • Pipeline input for full automation ([PSCustomObject]@{AssetId; Labels})
  • -LabelKey / -LabelValue for single-label interactive use
  • Asset lookups cached per run to avoid redundant API calls

Signature

Import-ZNAssetLabel -CsvFilePath <string> [-AssetColumn <string>] [-DomainSuffix <string>] [-WhatIf] [-ApiKey <string>] Import-ZNAssetLabel -AssetId <string> -LabelKey <string> -LabelValue <string> [-WhatIf] [-ApiKey <string>]
