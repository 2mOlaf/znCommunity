Break Glass Scripts

PowerShell 7+ Emergency Use Network Segment Identity Segment OT Connector Assets

The Zero Networks Break Glass scripts provide emergency access recovery when Zero Networks Segment Server, the portal, or IdP is unavailable or blocking critical access. They directly modify firewall rules, WFP filters, and (for OT) network switch ACLs on targeted assets to restore connectivity. Assets monitored by Cloud Connector or Segment Connector instead of a Segment Server aren't reachable by these scripts at all — see Connector-Monitored Assets below.

Pre-installed scripts — not part of ZNTools The scripts documented here (BreakGlass.ps1 and OTBreakGlass.ps1) are bundled with the Zero Networks installer and are pre-installed on all Segment Servers at C:\Program Files\Zero Networks\Breakglass\. They are not distributed through the ZNTools PowerShell module. This document is a reference for those pre-installed scripts, plus NetworkSegmentationWfpBreakglass.ps1 (shipped with the Windows Cloud Connector) and manual procedures for connector-monitored assets — see Connector-Monitored Assets.
Warning These scripts bypass Zero Networks segmentation controls. Use only when the Zero Networks Cloud Break Glass feature is unavailable and immediate access is required. Document and audit every use.

When to Use

Prefer the Zero Networks portal Cloud Break Glass in all normal scenarios. Use these scripts only when:

  • The Zero Networks management plane is unreachable.
  • Cloud Break Glass cannot be triggered fast enough for a production incident.
  • You need to target a specific asset that is not visible in the portal.
  • OT switch ACLs must be removed and no portal access is available.

BreakGlass.ps1

Windows Linux Emergency

Synopsis

Restores network and/or identity access to segmented Windows and Linux assets by remotely modifying firewall rules, WFP filters, and Group Policy on each target. Linux assets are handled via either iptables or nftables depending on the firewall backend in use on each host.

Syntax

-- Windows assets (bulk) -- .\BreakGlass.ps1 -Windows -Mode { Privileged | All } [-Network] [-Identity] [-PrivilegedPort <int[]>] [-ServersOnly] [-DisableBlockRule] [-ADUserName <string>] [-ADSvcPassword <string> | -ADSvcSecurePassword <SecureString>] [-DeploymentClusterName <string>]
-- Linux assets (bulk) -- .\BreakGlass.ps1 -Linux -Mode { Privileged | All } [-Network] [-PrivilegedPort <int[]>] [-LinuxUseSSHKey] [-LinuxSSHKeyPath <string>] [-ServersOnly] [-DisableBlockRule] [-LinuxUserName <string>] [-LinuxSvcPassword <string>] [-DeploymentClusterName <string>]
-- Windows AND Linux assets (bulk) -- .\BreakGlass.ps1 -WindowsAndLinux -Mode { Privileged | All } [-Network] [-Identity] [-PrivilegedPort <int[]>] [-LinuxUseSSHKey] [-LinuxSSHKeyPath <string>] [-ServersOnly] [-DisableBlockRule] [-ADUserName <string>] [-ADSvcPassword <string> | -ADSvcSecurePassword <SecureString>] [-LinuxUserName <string>] [-LinuxSvcPassword <string>] [-DeploymentClusterName <string>]
-- Single asset by name -- .\BreakGlass.ps1 -Asset <string> { -Windows | -Linux } -Mode { Privileged | All } [-Network] [-Identity] [-PrivilegedPort <int[]>] [-DisableBlockRule] [-LinuxUseSSHKey] [-LinuxSSHKeyPath <string>] [-ADUserName <string>] [-ADSvcPassword <string> | -ADSvcSecurePassword <SecureString>] [-LinuxUserName <string>] [-LinuxSvcPassword <string>]
-- Single asset by IP address -- .\BreakGlass.ps1 -IPAddress <string> { -Windows | -Linux } -Mode { Privileged | All } [-Network] [-Identity] [-PrivilegedPort <int[]>] [-LinuxUseSSHKey] [-LinuxSSHKeyPath <string>] [-ADUserName <string>] [-ADSvcPassword <string> | -ADSvcSecurePassword <SecureString>] [-LinuxUserName <string>] [-LinuxSvcPassword <string>]

Examples

Example 1 Open privileged ports on all Windows assets (network segment) 
PS> .\BreakGlass.ps1 -Windows -Mode Privileged -Network
Connects to every Windows asset in segmentedAssets.json that has network segmentation active. Opens inbound TCP 3389, 5985, 5986, 9389, and 445 via Windows Firewall and WFP. Credentials are prompted interactively per AD domain (and per OU if configured).
Example 2 Open all ports on Linux servers using SSH key 
PS> .\BreakGlass.ps1 -Linux -LinuxUseSSHKey -Network -Mode All -ServersOnly
Targets only Linux server-type assets. Uses an SSH key for authentication (path prompted at runtime). Each asset's AppliedFirewallType from segmentedAssets.json determines whether iptables or nftables is used. Inserts an ACCEPT-all rule on each target.
Example 3 Single Linux server by hostname using SSH key 
PS> .\BreakGlass.ps1 -Asset linuxserver.contoso.local -Linux -LinuxUseSSHKey -Network -Mode All
Resolves linuxserver.contoso.local via DNS and runs break glass against that single host. Because the firewall type is unknown for a manually-specified asset, both iptables and nftables backends are attempted. A failure on one backend does not abort the other. The SSH key path is prompted interactively.
Example 4 Single Windows asset by IP address (interactive credentials) 
PS> .\BreakGlass.ps1 -IPAddress 1.1.1.1 -Windows -Network -Mode All
Resolves 1.1.1.1 via a PTR record, then prompts interactively for a domain name and AD username before opening all ports on the target.
Example 5 Single Windows asset by IP address (explicit credentials) 
PS> .\BreakGlass.ps1 -IPAddress 1.1.1.1 -Windows -Network -Mode All `
         -ADUserName contoso.local\Administrator -ADSvcPassword P@ssw0rd
Same as Example 4 but supplies credentials non-interactively. Suitable for scripted or automated break glass runbooks.
Example 6 Explicit credentials without a plain-text password 
PS> $secure = Read-Host 'AD password' -AsSecureString
PS> .\BreakGlass.ps1 -IPAddress 1.1.1.1 -Windows -Network -Mode All `
         -ADUserName contoso.local\Administrator -ADSvcSecurePassword $secure
Same effect as Example 5, but the password never exists as a plain string in the command line or in session history. Prefer this form in runbooks and anywhere the command may be logged.
Example 7 Open a custom port set instead of the Privileged defaults 
PS> .\BreakGlass.ps1 -Windows -Mode Privileged -Network -PrivilegedPort 3389,5985
Opens only RDP and WinRM HTTP rather than the full default set (3389, 5985, 5986, 9389, 445). Use this to keep the break glass blast radius as small as the incident allows. -PrivilegedPort is ignored with -Mode All.
Example 8 Fully non-interactive single Linux asset via SSH key 
PS> .\BreakGlass.ps1 -Asset linuxserver.contoso.local -Linux -LinuxUseSSHKey `
         -LinuxSSHKeyPath C:\keys\id_rsa -LinuxUserName root -Network -Mode All
Supplying both -LinuxSSHKeyPath and -LinuxUserName removes every runtime prompt, so the run is scriptable. Both iptables and nftables are attempted, as with any single-asset Linux run.
Example 9 Scope to a single deployment cluster 
PS> .\BreakGlass.ps1 -Windows -Mode All -Network -DeploymentClusterName "zero.local"
Restricts the affected asset pool to the zero.local deployment cluster only. Assets in other clusters are skipped entirely. Use Tab to cycle through available cluster names.

Outputs

The script writes two text files to the current directory on completion:

FileContents
success_list.txtOne FQDN per line for every asset successfully processed.
failed_list.txtOne FQDN + error message per line for every asset that failed.

Console output shows connection status, applied rules, and any warnings in real time as each asset is processed (up to 100 assets in parallel).

OTBreakGlass.ps1

OT Cisco IOS-XE Emergency

Synopsis

Removes Zero Networks ACLs and optionally NetFlow monitoring from Cisco IOS-XE switch interfaces via RESTCONF, restoring unrestricted traffic flow on OT network segments.

Syntax

.\OTBreakGlass.ps1 [-SwitchPassword <SecureString>] [-RemoveMonitoring]

Parameters

-SwitchPassword

A single shared password used for all switches. When provided, the script skips per-switch password prompts. Accepts a SecureString — pass using Read-Host -AsSecureString or ConvertTo-SecureString if scripting non-interactively. If omitted, the script prompts for each switch's password individually based on the switch list in C:\Program Files\Zero Networks\Breakglass\switches.json.

Type:SecureString
Required:Optional
Default:None (per-switch prompt)
Pipeline input:False
-RemoveMonitoring

In addition to removing ACLs, also removes Zero Networks NetFlow monitoring (IP flow records tagged zeroNetworks*) from switch interfaces. Without this switch, only ACLs are removed and monitoring continues.

Type:Switch
Required:Optional
Default:False
Pipeline input:False

Examples

Example 1 Remove ACLs only (prompt per switch) 
PS> .\OTBreakGlass.ps1
Reads all switches from switches.json. Prompts for each switch's password individually, then connects to each over RESTCONF (HTTPS) and removes any ACL named zeroNetworks* from all interfaces. NetFlow monitoring is left in place.
Example 2 Remove ACLs and monitoring (shared password) 
PS> .\OTBreakGlass.ps1 -RemoveMonitoring -SwitchPassword (Read-Host "Switch password" -AsSecureString)
Uses a single shared password for all switches and additionally removes Zero Networks NetFlow monitors from all interfaces after removing ACLs.

Connector-Monitored Assets

Windows macOS (Unconfirmed) Linux (Unconfirmed) Emergency

Overview

BreakGlass.ps1 above only reaches assets a Segment Server knows about — it builds its target list from segmentedAssets.json and connects to each asset outbound over WinRM or SSH from the Segment Server itself. Assets monitored instead by Cloud Connector (assetStatus 7) or Segment Connector / Lightweight Agent (assetStatus 14) are never in that inventory, and are frequently not even reachable from a Segment Server — Cloud Connector in particular is commonly used for assets outside the corporate network: roaming laptops, cloud workloads, and other externally-hosted resources.

There is no bulk or remote break-glass path for these assets today. Recovery has to happen locally on the asset, logged in as a local administrator (Windows) or root (macOS / Linux, once a shipped script is confirmed for those platforms — see macOS and Linux Connector Assets).

This may extend to remote tooling — but plan for local, by hand Recovery here could eventually be driven through whatever configuration-management or MDM tooling manages the connector fleet (Intune, Jamf, Ansible, GPO, an RMM, etc.). In an actual incident you frequently won't know which of those is in place, whether it's currently reachable, or whether the incident itself is what's making it unreachable. The steps below assume none of that and are written to be run by hand, logged in locally at the console.

WFP-Based Windows Connector Assets

Applies when the Windows Connector agent enforces network segmentation using WFP (Windows Filtering Platform) — the same underlying mechanism BreakGlass.ps1 uses for Segment Server-monitored Windows assets, just reached completely differently here.

Script: NetworkSegmentationWfpBreakGlass.ps1 Shipped with the Windows Cloud Connector for exactly this purpose — confirmed against internal documentation (Confluence: Local Breakglass Script Execution for WFP assets, Network Segmentation - Windows - WFP Implementation). Internally it's called "Standalone Breakglass (Removal)" — the offline equivalent of "Restore Default Policy." Unlike BreakGlass.ps1's -Mode-scoped, additive allow filters, this script performs a full teardown: it deletes every WFP filter tagged with the Zero Networks NetSeg provider key (bf75ec5a-587c-43fc-b041-2f2283f45cfa), regardless of port or direction. There is no partial or scoped version of this action.
Monitoring typeLocal script path
Cloud Connector C:\Program Files\Zero Networks\CloudConnector\WindowsColletor\NetworkSegmentationWfpBreakGlass.ps1
Segment Server (Trust-monitored) C:\Windows\System32\config\systemprofile\AppData\Local\ZeroNetworks\Dependencies\NetworkSegmentation\WfpBreakglass.ps1
"WindowsColletor" is spelled that way in the actual path The Cloud Connector folder name is missing a "c" (WindowsColletor, not WindowsCollector) — confirmed identically across two independent internal docs, so this isn't a documentation typo. Type it exactly as shown or Tab-complete it; a corrected spelling will 404.

The second row is a bonus, not the main subject of this section: Segment Server-monitored ("Trust-monitored") Windows assets carry the same removal script locally too, under a different path — a local fallback if WinRM to that asset is unavailable and BreakGlass.ps1 can't reach it remotely either.

What it does

  1. Compiles a small embedded C# helper (ZeroNetworks.Breakglass.WfpRemover) in memory via Add-Type, using the same isolated-%TEMP% compile pattern as the Segment Server WFP break glass code.
  2. Opens a WFP engine handle and enumerates every filter on the system, regardless of which provider installed it.
  3. Keeps only the filters whose providerKey matches the Zero Networks NetSeg provider (bf75ec5a-587c-43fc-b041-2f2283f45cfa), printing each one it marks for removal by name as it goes.
  4. Deletes all matched filters inside a single WFP transaction (all-or-nothing commit).
  5. Prints Done. on success, or No filters to remove if the asset isn't currently enforcing via WFP at all (try Windows Firewall-Based Connector Assets instead) or is already clear.
Scope This only removes filters under the NetSeg provider key above — it does not remove the Zero Networks NetSeg sublayer or provider objects themselves, only the filters inside them. It also does not touch Windows Firewall rules, and does not touch identity segmentation — whether identity segmentation applies to Connector-monitored Windows assets, and how to break-glass it if so, is not yet confirmed for this document.

Syntax

.\NetworkSegmentationWfpBreakGlass.ps1

No parameters — running the script is the entire action.

Running it locally

  1. Get onto the asset itself — console, KVM, or whatever out-of-band access is available. This does not use WinRM or any remote transport; it must run on the target.
  2. Open PowerShell as Administrator. Windows PowerShell 5.1 (in-box on Windows 8 / Server 2012 and later) is sufficient — the script has no #Requires -Version 7 and uses only APIs available since PowerShell 2.0 / .NET Framework.
  3. If the script was copied from another machine (USB, share, email), Windows may block it as downloaded content. The internal support KB's documented fix is Set-ExecutionPolicy Unrestricted -Scope CurrentUser; Unblock-File or a one-off -ExecutionPolicy Bypass invocation both work too.
  4. Run it and confirm the output lists the filters removed (or No filters to remove) and ends with Done. To verify independently of the script's own output, run netsh wfp show state and confirm no filters remain under the NetSeg provider.
  5. Validate the connection that was failing.
Set execution policy, then run (per the internal support KB) 
PS> Set-ExecutionPolicy Unrestricted -Scope CurrentUser
PS> .\NetworkSegmentationWfpBreakGlass.ps1
…or run once without changing execution policy 
powershell.exe -ExecutionPolicy Bypass -File .\NetworkSegmentationWfpBreakGlass.ps1
This only sticks while the asset can't reach the Zero Networks cloud The Connector runs an anti-tampering check on its WFP filters roughly every 10 minutes, plus immediately on a filter-change event — internal guidance puts the reaction time at seconds, not minutes, whenever the collector is actually up and connected. Per the internal FAQ: "The break glass script can be run to open privileged ports… or open Any<->Any. When the service comes back online, antitampering will disable the break glass rule." In other words: this is specifically for when the asset's connectivity to the Zero Networks cloud is down (which is presumably why you're here instead of using the portal). Once that connectivity is restored, expect Zero Networks to revert this on its own — that's by design, not a bug to work around. Still confirm it actually happened rather than assuming it. This removes all NetSeg WFP filters in one shot — there's no way to scope it to a port list the way -PrivilegedPort does for BreakGlass.ps1. Document and audit every use.

Windows Firewall-Based Connector Assets

Applies when the Connector agent enforces segmentation using the native Windows Firewall (netsh advfirewall / New-NetFirewallRule) instead of WFP. No break-glass script is currently shipped for this path — the steps below are manual, run locally as an Administrator.

This only sticks while the asset can't reach the Zero Networks cloud Same anti-tampering behavior as the WFP case above: while the Connector service is up and connected, it disables foreign (non Zero Networks) rules and restores its own — internal guidance describes this as happening within seconds. A manually-added allow rule isn't competing with a specific Zero Networks block rule so much as it's competing with an agent that actively re-asserts its own rule set. This procedure only makes sense when the asset genuinely can't reach the cloud right now; if it can, use the portal's Cloud Break Glass instead — your local change will likely be reverted before you can use it.
Zero Networks' own rule naming (confirmed) Every rule the collector creates is prefixed ZN-: ZN-Rule (the actual allow rules — name also encodes rule id / protocol / checksum / version), ZN-RuleMeta (metadata-only, no live rule), ZN-Icmp, ZN-Policy, ZN-Cloud-Addresses (outbound access to the ZN cloud — do not touch this one), and ZN-Unprotected-In / ZN-Unprotected-Out (the agent's own allow-all rules, created automatically on a normal unsegment). Also watch for ZN-States — it marks the asset as segmented and doubles as the inbound allow for the Segment Server on WinRM 5985 and ADWS 9389, so disabling it can cut off the very management path you might need later.

Option A — netsh advfirewall (any Windows version, any shell)

The universal fallback — no PowerShell version dependency at all.

Add any-to-any allow rules 
netsh advfirewall firewall add rule name="ZN Break Glass - Allow All Inbound" dir=in action=allow protocol=any remoteip=any enable=yes
netsh advfirewall firewall add rule name="ZN Break Glass - Allow All Outbound" dir=out action=allow protocol=any remoteip=any enable=yes

To find Zero Networks' own rules by the confirmed ZN- prefix:

List Zero Networks rules, then disable one 
netsh advfirewall firewall show rule name=all | findstr /i "Rule Name: ZN-"
netsh advfirewall firewall set rule name="<exact ZN- rule name>" new enable=no

Option B — PowerShell (NetSecurity module, PowerShell 5.1 baseline)

Version note The NetSecurity module is built into Windows PowerShell 5.1 (in-box on Windows 8 / Server 2012 and later) — treat 5.1 as the floor for these commands, not PowerShell 7. On Windows 7 / Server 2008 R2 with only PowerShell 2.0–4.0, NetSecurity isn't available — use the netsh commands in Option A instead.
Review Zero Networks' rules first 
PS> Get-NetFirewallRule -DisplayName "ZN-*" |
    Select-Object DisplayName, Direction, Action, Enabled
Add any-to-any allow rules (both directions) 
PS> New-NetFirewallRule -DisplayName "ZN Break Glass - Allow All Inbound" -Direction Inbound -Action Allow -Protocol Any -RemoteAddress Any -Enabled True
PS> New-NetFirewallRule -DisplayName "ZN Break Glass - Allow All Outbound" -Direction Outbound -Action Allow -Protocol Any -RemoteAddress Any -Enabled True
Disable a Zero Networks rule by its confirmed prefix (never ZN-States) 
PS> Get-NetFirewallRule -DisplayName "ZN-Rule*" | Disable-NetFirewallRule

Option C — GUI (Windows Defender Firewall with Advanced Security)

  1. Run wf.msc as Administrator.
  2. Right-click Inbound Rules → New Rule… → Custom → All programs → protocol type Any → leave the local/remote IP scope as Any → Allow the connection → apply to all profiles → name it (e.g. ZN Break Glass - Allow All Inbound).
  3. Repeat under Outbound Rules.
  4. Sort the rule list by name to find the agent's own ZN- rules if you need to disable one directly (right-click → Disable Rule) — skip ZN-States, see above.
If the collector is still running, none of this will hold A local administrator can currently stop the Cloud Connector's own Windows service — find it with Get-Service | Where-Object DisplayName -like "*Zero Network*" (exact service name not confirmed for this document; check what it resolves to on your build before an incident). Stopping it is the only way documented here to keep manually-added rules from being reverted while the asset otherwise has connectivity. Disabling the firewall profile(s) entirely is the blunter alternative, and removes all protection on the asset, not only Zero Networks': netsh advfirewall set allprofiles state off / ... state on to restore, or in PowerShell 5.1+ Set-NetFirewallProfile -All -Enabled $false / Set-NetFirewallProfile -All -Enabled $true. Either way, treat this as a last resort and turn it back on as soon as the incident allows.

Cleaning up

Per the same internal FAQ cited above, Zero Networks' anti-tampering is expected to revert manually-added rules automatically once the asset's cloud connectivity is restored — that's the same mechanism that reverts the WFP case. Still, confirm it rather than assume it, especially if you disabled a ZN- rule directly rather than only adding allow rules alongside it.

Remove the break-glass rules / re-enable what you disabled 
# netsh
netsh advfirewall firewall delete rule name="ZN Break Glass - Allow All Inbound"
netsh advfirewall firewall delete rule name="ZN Break Glass - Allow All Outbound"

# PowerShell 5.1+ NetSecurity equivalent
PS> Remove-NetFirewallRule -DisplayName "ZN Break Glass - Allow All Inbound"
PS> Remove-NetFirewallRule -DisplayName "ZN Break Glass - Allow All Outbound"
PS> Get-NetFirewallRule -DisplayName "ZN-Rule*" | Enable-NetFirewallRule
# and restart the Connector service if you stopped it

macOS and Linux Connector Assets

Not yet confirmed No Zero Networks-shipped break-glass script has been confirmed for Segment Connector (Linux) or Cloud Connector (macOS) assets as of this writing. Linux (Segment Connector / Lightweight Agent)

BreakGlass.ps1 already handles Linux assets over iptables or nftables for Segment Server-monitored hosts (see BreakGlass.ps1 above) — the same two backend families are the likely candidates for Connector-managed Linux assets, but this isn't confirmed. Inspect the live ruleset before changing anything:

Inspect the current ruleset 
sudo iptables -L -n -v --line-numbers
sudo nft list ruleset

If an iptables-style ruleset is in use, an ACCEPT-all insert mirrors what BreakGlass.ps1 does remotely for -Mode All:

iptables ACCEPT-all insert 
sudo iptables -I INPUT 1 -j ACCEPT
sudo iptables -I OUTPUT 1 -j ACCEPT

For nftables, the exact table and chain names depend on what's actually installed — confirm with nft list ruleset first, then insert an accept rule ahead of any existing drop/reject rule in the relevant chain(s).

macOS (Cloud Connector)

The enforcement mechanism used by the macOS Cloud Connector isn't confirmed in this documentation set. macOS's native firewall stack is Packet Filter (pf, driven via pfctl); if segmentation turns out to run over a pf anchor, disabling just that anchor (once its name is confirmed) would be the targeted equivalent of the Windows and Linux techniques above. Disabling pf entirely is the untargeted last resort — same caveat as turning off Windows Firewall — since it removes all packet filtering on the host, not only Zero Networks'.

Inspect, then flush a confirmed anchor (or disable pf entirely) 
# inspect current rules/anchors first
sudo pfctl -s all

# flush a confirmed Zero Networks anchor
sudo pfctl -a <anchor-name> -F all

# last resort: disable pf entirely
sudo pfctl -d

Notes

  • Rules and filters added by the break glass scripts are persistent across reboots. They must be manually removed or will be cleaned up when the Zero Networks agent next synchronises policy.
  • For Windows assets the script uses PowerShell Remoting (WinRM) with Negotiate authentication. Ensure WinRM is enabled and accessible on targets.
  • For Linux assets the script connects via SSH using the POSH-SSH module, escalates to root with sudo su, and manipulates the firewall through a Zero Networks Python virtual environment bundled on the asset. Both iptables (via python-iptables) and nftables (via python-nftables) backends are supported. For bulk operations, the backend is selected from AppliedFirewallType in segmentedAssets.json. For single-asset operations (-Asset / -IPAddress), both backends are attempted; a failure on one does not abort the other.
  • Both scripts create success_list.txt and failed_list.txt (or ot_success_list.txt / ot_failed_list.txt for OT) in the working directory.
  • Bulk operations run with -ThrottleLimit 100 (up to 100 assets processed concurrently).
  • The Privileged-mode port sets are defined as the WindowsPrivilegedPort and LinuxPrivilegedPort enums inside the script, and can be overridden for a single run with -PrivilegedPort.
  • segmentedAssets.json is only loaded for bulk operations. Single-asset runs (-Asset / -IPAddress) do not read the inventory file.
  • The segmentedAssets.json file is automatically generated and kept up to date by the Zero Networks Segment Server. It is read from C:\Program Files\Zero Networks\Breakglass\ on the machine running the script. Do not edit it manually.
  • For OT, switch credentials are never stored; they are held in memory only for the duration of the script run and cleared afterwards.
  • Assets monitored by Cloud Connector or Segment Connector are never in segmentedAssets.json and are out of scope for BreakGlass.ps1 entirely — see Connector-Monitored Assets.

Change Manifest

Version History

Functional changes to BreakGlass.ps1 that shipped without separate release notes, plus documentation corrections applied to this reference. Newest first.

AreaChangeImpact
Linux firewall backend Added nftables support alongside iptables. The backend is selected per-asset from AppliedFirewallType in segmentedAssets.json for bulk operations. Required for modern Linux distributions (e.g. RHEL 10) that ship without iptables-legacy.
Single-asset Linux (-Asset / -IPAddress) Both iptables and nftables backends are now attempted automatically in sequence. Each attempt is isolated; a failure on one backend does not abort the other. Eliminates the need to know which backend is active when targeting a single Linux host manually.
Linux Privileged mode ports Expanded from SSH (22) only to SSH (22), Telnet (23), and SMB (445) via multiport match. Restores management access for environments that require SMB or legacy Telnet alongside SSH.
Windows Privileged mode ports Expanded from RDP (3389) only to RDP (3389), WinRM HTTP (5985), WinRM HTTPS (5986), ADWS (9389), and SMB (445). Applied at both the Windows Firewall and WFP layers. Enables PSRemoting, AD management tooling, and file access in a single Privileged-mode run — previously a second -Mode All run was needed to restore WinRM access.
segmentedAssets.json loading The inventory file is now only loaded for bulk operations. Single-asset runs (-Asset / -IPAddress) skip the load entirely. Avoids a misleading error if the JSON is stale or absent when targeting a known asset directly.
-PrivilegedPort New parameter. Replaces the built-in Privileged-mode port sets with an explicit TCP port list (1–65535 each) for both Windows and Linux. Warns and is ignored under -Mode All. Lets an operator open a narrower set of ports than the defaults during an incident.
-LinuxSSHKeyPath New parameter. Supplies the SSH private key path non-interactively; requires -LinuxUseSSHKey and conflicts with -LinuxSvcPassword. The path is validated at parameter binding. Makes key-based Linux runs fully scriptable — no runtime prompt for the key path.
-ADSvcSecurePassword New parameter. SecureString alternative to -ADSvcPassword; the two are mutually exclusive and either one satisfies -ADUserName. Keeps the AD password out of the command line and session history in scripted runs.
-ADUserName Accepts UPN format (user@domain.com) in addition to DOMAIN\user. Both formats parse correctly when supplying explicit credentials for bulk Windows operations.
-DeploymentClusterName Tab-completion reads live cluster names from segmentedAssets.json; the parameter also validates against that list and throws a descriptive error with valid options on mismatch. Tab-complete with Tab in PowerShell 7+. Names containing spaces are quoted automatically.
Windows credential collection (bulk) Per-OU credentials are collected and matched at runtime. The script reads OuCredentials from each domain in ForestsConfig and prompts separately for each OU. Assets with an OrganizationalUnit field are matched to the appropriate OU credential before falling back to the domain credential.
